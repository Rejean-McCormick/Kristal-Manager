# SemantiK Phrase Ops Console v0.4.0
## SA capability contract + verifiable GF Wordbench handoff

This release reconnects the multilingual compact lab to the existing ecosystem authorities instead of growing Phrase Ops into a second language architecture.

Key changes:
- The multilingual capability profile is now **baseline-only** (`semantik-multilingual-core-lab-2`): `clause.passive_event` is no longer required globally.
- The technical probe still exercises all 128 cases, but a second SemantiK Architect conformance pass evaluates only the **advertised** capabilities.
- Per-language optional support is carried through SA candidate `extension_capabilities`; for the v0.3.4 capability policy this means **121 advertised cases + 7 disabled cases**.
- Phrase Ops therefore reports two distinct truths: `128/128` technical diagnostic coverage and `121/121` advertised SA capability conformance.
- New button **14 — Préparer handoff Wordbench — active16** builds a hash-bound `semantik-wordbench-handoff-v1` bundle and immediately asks the configured GF Wordbench to inspect it.
- The handoff is always `release_authorized=false` / `release_eligible=false`. Wordbench must reproduce GF/scenario evidence and perform its own hash-bound linguistic review before any release decision.
- The former local linguistic review is explicitly renamed **pré-revue locale** (buttons 15/16). It remains useful diagnostics but is not the linguistic release authority.
- Legacy French release buttons remain separate and must not be confused with active16.

Required companion versions:
- SemantiK Architect **1.2.0+** (candidate `extension_capabilities`)
- GF Wordbench **1.4.0+** (`semantik_handoff` inspector)

Expected active16 sequence:
1. Button 1 — preflight.
2. Button 13 — real GF compile + technical 128/128 + advertised SA capability conformance 121/121 + migration gate.
3. Button 14 — build and verify Wordbench candidate handoff.
4. Continue linguistic validation in GF Wordbench. Phrase Ops does not authorize release or activation.

## v0.3.1.1 — invalidation fail-closed du cache de reprise

La v0.3.1.1 corrige un défaut du `--resume-successful` observé après l'installation de v0.3.1 : un rapport v0.3.0 techniquement complet pouvait être réutilisé alors que les concretes compacts avaient changé. Ce correctif ne change aucune règle linguistique de v0.3.1. Il garantit seulement que les huit corrections V3 sont réellement recompilées et mesurées avant que le gate puisse passer.

## v0.2.6 — resolver RGL strict

Le resolver multilingue ne traite plus chaque identifiant GF comme un nom de module. Il suit uniquement les références de modules présentes dans les positions syntaxiques pertinentes : composition de module, `open ... in` et références qualifiées `Module.symbole`. Quand plusieurs fichiers portent le même nom de module, un seul candidat est choisi avec priorité au répertoire source, au répertoire de la langue et aux racines communes configurées.

Cela évite d’ajouter par collision de nom des répertoires sans rapport comme `rukiga`, `icelandic`, `exper`, `tagged` ou `stemmed`, sauf s’ils sont réellement référencés par la chaîne de modules. Le rapport JSON expose `rgl_dependency_resolver: strict-v2`. La reprise conserve les succès précédents et ne recompile que les langues incomplètes.

## v0.2.5 — parallélisme GF + interface entièrement défilable

Les boutons **13** et **15** parallélisent désormais la phase coûteuse de compilation GF par langue. Le réglage **Performance du banc multilingue → Parallélisme GF** propose `Auto`, `1`, `2`, `4`, `6` ou `8` workers. `Auto` utilise au maximum 4 workers et tient compte du nombre de CPU logiques disponibles. Les compilations restent isolées dans leur répertoire de build par langue; la phase `CandidateMatrixConformance` reste volontairement séquentielle.
